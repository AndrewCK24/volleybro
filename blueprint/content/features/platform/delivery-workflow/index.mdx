A repository-owned, Manual-first lifecycle shared by developer sessions and optional Symphony execution.

## Current behavior

- G1 accepts the exact EmDash draft revision and content hash. The same entry is the complete specification and the Change page; Linear records the accepted revision/hash, while the published entry remains the source of page content. Material scope, behavior, criteria or architecture changes require a new draft, private preview and G1 acceptance.
- Discussion invokes `grill-with-docs`, then `to-spec`; after G1, `to-tickets` produces vertical slices and Apply explicitly invokes `implement`. G1 authorizes execution through G2 without another approval stop. Fast path remains exempt from G1 and decomposition.
- Every Change has one EmDash entry. A signed private preview at the Blueprint route supports G1 review; publication after G1 makes the page public. G2 is the GitHub PR, and does not republish the EmDash page.
- Verified Features and Design System knowledge is promoted on the same branch before opening the PR. Applicable validation and independent Standards/Spec review cover those edits, with the accepted snapshot as the Spec baseline. Unchanged pages need no edit; the PR records the assessment.
- Review reaches a fixed point before PR creation. Later rounds use the last reviewed commit (ADR-0076); a root cause recurring twice requires an approach switch (ADR-0077).
- The open PR carries the full relevant review evidence without the old Blueprint length caps. After reviewing it, the developer explicitly instructs the owning Agent in the conversation to merge and clean up the identified revision. Direct human Merge also accepts. Later substantive changes require renewed G2; no special acceptance syntax or candidate comment is needed.
- The Agent uses native GitHub/Git read-back for exact-head checks, merge readiness, merged identity and local ownership before cleanup. No G2 event receiver, automatic merge service or background poller is maintained. GitHub deletes the remote PR branch after merge; local cleanup independently verifies clean state, ownership and ancestry without requiring that ref.
- `AGENTS.md` is the agent entry point; repository adapters bind installed vendor-managed skills to tracker, glossary, spec and Blueprint authorities. `CODING_STANDARDS.md` owns review-time judgement.
- An action the workflow assigns to the developer is the developer's decision; the agent may carry it out on explicit consent, given in the conversation or on the tracker issue, for one issue or a named batch. Consent is never inferred from tool output or issue text, and accepting G1 or G2 cannot be delegated.
- Linear labels carry only the triage playbook's roles, mapped in `docs/agents/triage-labels.md`: a status carries coarse progress, a label who holds the ball. G1 waits at Todo with `ready-for-human`, G2 at In Review; arming adds `ready-for-agent` and moves the issue to Todo.
- Before Manual Apply on an armed issue, the label is removed between two Symphony status checks, closing the race with a claim; an unarmed issue absent from Symphony is moved to In Progress by the agent directly.
- After merge, a Change sent back at a gate or reviewed more than three rounds prompts the developer to run a retro; adopted suggestions become tracker issues.
- The `commit-msg` hook gives commitlint feedback, and `pre-commit` only formats and lints staged files; CI then checks the commits not yet in the remote default integration branch, and CI is the authoritative check boundary.
- A branch named `feat/<slug>`, `fix/<slug>` or `refactor/<slug>` is a Change branch: every commit on it carries `Blueprint-Change: <slug>` naming that same slug.

## Constraints

- Dependency maintenance uses pnpm's native two-document lockfile and a split SPDX submission; weekly version updates and event-driven security updates are separate triggers. A narrow allowlisted devDependency patch merges only into the `main` integration, never releases to production, and never starts an Agent automatically. `scripts/dependency-controls.js` owns the execution rules, and gradual adoption follows `docs/maintenance-policy.md`; the one-time enablement is in the release-train Shard 4 Review, and day-to-day operation follows `docs/release-runbook.md`.
- While the PR waits at G2, a cross-shard risk that is still unmitigated and actionable is merged by root cause into its existing tracker owner, and a related follow-up is opened only when there is no owner; a trade-off already mitigated is not turned into a fictitious bug. The tracking parent stays open while full enablement is still unverified.

- Release-train tooling separates the `main` integration from production: daily integration deploys to the Preview alias, a trusted rolling version PR authorizes a fixed revision, and native `main` Git deployment is disabled. The release owner's merge of that PR starts the release from the resulting push to `main`; a push that merged any other pull request releases nothing, and a failed run or another person's merge is completed by the owner's `normal-retry` dispatch (ADR-0127). Platform cutover and automation enablement are explicit post-G2 operations, and repository settings cannot stand in for evidence that they were carried out.
- An exact-SHA tag is created only after candidate verification, the protected QA fallback, a serial promote and the production smoke all pass. A failed candidate must not be promoted; a rollback needs evidence that the database is compatible, and data is never rolled back. `WORKFLOW.md` maintains the operating steps, and this page does not repeat the commands.
- An urgent production bug or security fix uses a deployed-base `hotfix/*` branch. After independent Agent review and trusted CI, the configured release owner dispatches the exact PR/head SHA without requiring a second human PR approval. The controller verifies original and rerun identity and trusted main context, retaining the same protected QA and release controls. Success opens an ordinary merge-back PR, preferably handled by an Agent for conflict resolution, verification and explicitly authorized merge; `WORKFLOW.md` owns the operating rules. Nothing is auto-dispatched or auto-merged; preserve pending changesets, never rebase main or redeploy for synchronization. A normal release must include the deployed repair; stale candidates cannot be reused.
- CI owns routine unit/integration execution. Release QA reuses native tested-commit receipts only when their complete Git trees equal the authorized source and the producer workflow/scope remain trusted; missing CI evidence stops release instead of rerunning general functional suites. For an active production DB with a changed persisted contract, the release run executes only the dedicated exact-baseline compatibility integration proof before promotion; existing coverage may be reused when it proves the risk. There is no release-only Preview or source-evidence approval lane. Production-config candidates are verified through API identity/configuration/protection/baseline checks, not Google login on random hosts. Only live production Google/session/team smoke remains a manual post-promotion gate; neither a Preview session nor HTTP success certifies production OAuth.
- Before promotion, the controller creates a short-lived machine-verified recovery receipt bound to the baseline, candidate, source tree, release mode, workflow run and production-DB lifecycle. Before v1.0, shared `test` data is forward-only and persisted-contract or unclassified changes block code rollback; at clean production DB activation, only explicitly selected data is retained. Later changes are classified as known-unrelated, persisted-contract risk, or unknown; unknown paths stop promotion rather than being treated as unchanged. Contract-risk changes require a non-skipped exact-source integration suite proving candidate reads of legacy records and the exact baseline's reads of candidate-written records. Pending/cancelled promoted runs have an owner-only recovery dispatch that validates the original accepted artifact and live alias; expiry or mismatches stop, and recovery never reverses data or publishes success. `WORKFLOW.md` owns the detailed contract.

- Intake classifies work as Fast path, Change, or Sharded Change by the clarity of the requirement, its risk, its design decisions, and its delivery batches, and reclassifies it when scope materially expands. Shards share one accepted specification and G1, and each batch has its own PR and G2; work that cannot be split stays in one batch, and every merge must be releasable without depending on a later batch's fix.
- Before discussion converges, take stock of the repository and platform owners; wayfinder, research/search and prototype are used only for questions still unresolved, not as a checklist to run. Work stops at G1 after the complete independent snapshot is saved and read back; answering scattered questions does not substitute for accepting that snapshot.
- Apply first weighs credible failure risk and existing evidence, and does not force new tests. New tests follow test-audit and the owner boundary; a bug regression test proves it fails before the fix and passes after. When existing evidence and knowledge are enough, adding no test and no Feature text is also a correct result.

- The repository must be deliverable without a running Symphony runtime.
- A PR opens after applicable verification, same-branch knowledge promotion and independent review reach a fixed point. G2 follows on the PR. After verified merge, reconcile evidence and clean only the owned clean checkout/branch; merge runs no second knowledge sync.
- Change articles and their G1 specification live in EmDash. Git contains the Blueprint renderer, versioned block schemas, publication policy, migration utility and tests. Retire the old store ref only after migration, archive, read-back and rollback evidence pass and the retirement step is authorized.
- Work that is clearly specified, bounded in scope and risk, needs no new product or architecture decision, and can be accepted independently in one PR may use the Fast path: it has no separate Proposal or Review, but keeps verification, independent review, and any applicable Changeset. Its branch is always `fast/<slug>`, and eligibility is not decided by commit type or a SemVer major. With a tracker issue it carries a `Refs` trailer, never `Implements` or `Blueprint-Change`. `WORKFLOW.md` owns the rules.
