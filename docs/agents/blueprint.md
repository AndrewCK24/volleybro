# Blueprint adapter

Blueprint presents current capability knowledge and optional visual supplements. `WORKFLOW.md` owns sequencing and gates; `docs/agents/issue-tracker.md` owns accepted specifications. Blueprint stays tracker-neutral.

## Optional Proposal

Create a Change page only when a needed UI mockup or a complex change to an app/user/other process benefits from an interactive flowchart. A Proposal supports human comprehension of the accepted spec; it does not duplicate the full spec or become G1/G2 authority. G2 is always the GitHub PR and creates no Review page, even for a Change that has a Proposal.

```text
blueprint/content/changes/<slug>/
├── index.mdx       frontmatter: title, description, capabilities, visualOnly: true
├── proposal.mdx    focused visual supplement
├── design.tsx      optional interactive mockup
└── facts.json      generated by store publication
```

Only `index.mdx` is a route. New `visualOnly` pages have no mandatory TLDR/scenario export or Review sections. Introduce the visual's question, relevant states and interpretation briefly; use `InteractiveFlowchart` for complex process comparison and shared components for a retained mockup. Prefer captures or a disposable prototype when repeated interactive comparison is unnecessary. Link the accepted spec in the operational issue and PR; durable page text refers to the Change by slug without tracker-specific URLs.

Publish visuals through the existing `blueprint-changes` store with `pnpm blueprint:gate <slug>`; this proves the visual, not human acceptance. Main Blueprint is the default URL; use `--preview` for unmerged components, decisions or Features. Verify the hosted complete content hash and rendered identity before handoff. Any `design.tsx` retains the trusted Preview one-route declared-mode/client-render proof. Missing identity, mode, expected content or clean render evidence fails closed. Routine Agent browser review is unnecessary; inspect a page when the developer identifies a visual comprehension problem.

## Historical compatibility and shared rendering

All Change routes render Proposal directly, with no tabs. Existing Review and shard files remain read-only in collapsed footer disclosures; preserve `#proposal`, `#review`, `#review-s<N>` and inner anchors. A deep link opens enclosing disclosures. Keep legacy scenario results, review ordering, measurements, accepted contents and converted-history markers intact; these formats are compatibility inputs, not templates for new Changes.

The existing store, publication, pull and derived lifecycle overlays remain active; store retirement is separate work. Dev/build pull published pages. Before changing a shared component/API, pull the store, search all consuming Change pages and run a full Blueprint build with focused behavioral/parser checks where needed. Astro statically builds routes, retained mockups use React islands, and render failures emit `data-blueprint-render-error="true"`, which the hosted gate rejects. A successful hook/HTTP response alone proves no snapshot.

## Current knowledge and writing

Promote verified knowledge through `docs/agents/artifact-lifecycle.md` before the delivery PR, on the same branch. Use the narrowest Feature for capability behavior/constraints and the Design System authority for reusable UI/UX rules. Feature pages render records matching their exact capability IDs rather than copying decision text.

- Use an existing component only when it helps readers understand structure, comparison or interaction. Full skill outputs retain their relevant content without old Blueprint length caps.
- Correct affected visual meaning with the spec; a substantive contract change follows Ingest. Meaning-preserving presentation edits to a new visual supplement do not themselves require G1 again. Accepted historical page contents stay unchanged.
- Keep component string props plain, apart from supported backtick inline code; SVG flowchart labels remain plain text. Put SVG `<text>` content on the opening tag's line.
- Put MDX block component opening/closing tags on their own lines.
- Write Change prose in zh-tw with English technical terms; Features/Design System, scenario strings, ADRs and agent-facing documents use English.
- Titles name the Change, not a tab. Derive figures from generated facts rather than copying counts. Other-Change references and prose wrapping follow `CONTRIBUTING.md`.

## Writing a decision record

A record holds one decision, and governs either the product or the delivery process — the workflow, the Blueprint, tooling and documents — never both. Write one only when the decision is hard to reverse, would surprise a reader without its context, and came out of a real trade-off; an easily reversed or obvious choice needs no record.

The `decision` field states the decision itself in a few sentences; supporting detail belongs in `context` or `consequences`. A `decision` stays under 1000 characters; past that, split a record that bundles several decisions, or move detail out of a single decision's `decision` field. When neither applies, keep the record and put it to the developer at the gate with the reason.
